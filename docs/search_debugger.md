# Explainable Search Debugger

## Purpose

The **Explainable Search Debugger** is a diagnostic tool designed for Product Managers, Product Analysts, and Engineers to observe, evaluate, and explain why search queries succeed, fail, or trigger automated query relaxation.

In e-commerce search, black-box query rewriting often creates severe trust issues:
- Why did a 5-token query return 0 results?
- Which specific modifier caused strict keyword intersection to collapse?
- Why did the relaxation algorithm drop modifier $A$ instead of category noun $B$?
- Did the system preserve core category intent, or did it drift across departments?
- When all candidates fail, does the circuit breaker prevent irrelevant catalog pollution?

The search debugger provides complete transparency into token semantics, catalog document frequencies, candidate scoring, and safety guardrails, without altering underlying search algorithms.

---

## User Flow

The search debugger can be accessed via two developer- and PM-friendly interfaces:

1. **Interactive Web Dashboard** (`src/search_debugger_ui.py`):
   ```bash
   python src/search_debugger_ui.py --port 8080
   ```
   Opens a responsive single-page application at `http://localhost:8080/` featuring:
   - Query input with 5 one-click preset demo scenarios.
   - Dual-mode segmented toggle: **Product Manager View** vs. **Technical Diagnostics View** vs. **Complete View**.
   - Real-time KPI summary bar (health status badge, strict hits, recovered delta, latency breakdown).
   - Dynamic token semantic role matrix.
   - Multi-tier candidate fallbacks table with exact objective scores and safety verdicts.
   - Active guardrails verification checklist.
   - Responsive in-stock product cards.

2. **CLI Debugger** (`src/search_debugger.py` or `src/search_engine.py --debug`):
   ```bash
   python src/search_engine.py --debug "women floral midi dress red"
   python src/search_debugger.py --pm "women floral midi dress red"
   python src/search_debugger.py --tech "women floral midi dress red"
   python src/search_debugger.py --demo
   ```

## Architecture

The debugger adheres strictly to an **observational architecture**:

```
           User / PM / Engineer
                    │
      ┌─────────────┴─────────────┐
      ▼                           ▼
CLI Interface              Web Dashboard
(src/search_debugger.py)   (src/search_debugger_ui.py)
      │                           │
      └─────────────┬─────────────┘
                    ▼
          SearchDebugger Class
                    │
                    ▼
          LocalSearchEngine
        (src/search_engine.py)
                    │
      ┌─────────────┴─────────────┐
      ▼                           ▼
Strict Search Baseline     Query Relaxation Engine
(Doc Freq & Posting Lists)  (Multi-tier candidate eval)
                    │
                    ▼
          RelaxedSearchResponse
        (with candidate_evaluations)
                    │
                    ▼
          SearchDebugResult
   (Token Semantics + Guardrail Checks + Dual Explanations)
```

**Key Architectural Rule**: The debugger **never** duplicates search or relaxation logic. It invokes `LocalSearchEngine.search_with_relaxation()` and inspects computed catalog metadata.

## Debugging Information

For every analyzed query, the debugger exposes:

1. **Token Semantics & Catalog Frequencies**:
   - `token`: Original token string.
   - `normalized_token`: Stemmed term (via Porter-style heuristic).
   - `document_frequency`: Count of catalog products containing the token.
   - `token_role`: Semantic categorization:
     - `CORE_CATEGORY`: Protected category nouns (`women`, `men`, `dresses`, `jeans`, `shoes`).
     - `BRAND`: Registered catalog brands (`nike`, `adidas`, `puma`, `zara`, `h&m`).
     - `MODIFIER`: Secondary attributes (`floral`, `red`, `cotton`, `slim fit`).
     - `MISSING_CATALOG_TERM`: Terms with $\text{DF} = 0$ in the catalog (`midi`, unknown terms).
   - `is_core_term`: Boolean flag protecting the token from removal.
   - `is_candidate_modifier`: Boolean flag marking the token as droppable.

2. **Strict Search Baseline Diagnostics**:
   - In-stock result count and total catalog matches.
   - Execution latency in milliseconds.
   - Strict status: `NORMAL` ($\ge 3$), `LOW_RESULTS` ($1–2$), or `ZERO_RESULTS` ($0$).
   - Rule-based trigger diagnostic explanation.

3. **Multi-Tier Candidate Fallback Evaluations**:
   - Candidate fallback queries generated by the relaxation engine.
   - Dropped token(s) per candidate.
   - In-stock result count recovered by each candidate.
   - Category consistency verification flag.
   - Objective function candidate score.
   - Decision verdict: `SELECTED`, `SAFE`, or `REJECTED` (with explicit rejection reason).

4. **Active Guardrails Verification Matrix**:
   - `core_category_preserved`: Verifies category nouns were not dropped.
   - `in_stock_filtered`: Verifies all returned inventory is currently purchasable.
   - `minimum_token_overlap_satisfied`: Verifies $\ge 2$ tokens are retained.
   - `category_consistency_maintained`: Verifies master department consistency.
   - `circuit_breaker_activated`: Verifies unsafe fallbacks are suppressed.

## Product Manager View vs Technical View

| Dimension | Product Manager View (`--pm`) | Technical View (`--tech`) |
| :--- | :--- | :--- |
| **Primary Audience** | PMs, Analysts, Business Stakeholders, Interviewers | Search Engineers, Infrastructure Engineers |
| **Problem Formulation** | Natural language friction diagnosis | Strict match zero/low-result diagnostic |
| **Algorithm Action** | Decision narrative (e.g. "Relaxed modifiers 'midi', 'red'") | Document frequencies, candidate scores, dropped tokens |
| **Customer Impact** | Discovery recovery delta (+16 products) | In-stock result count, relevance scores |
| **System Health** | Executive trust & relevance summary | Guardrail checklist, latency breakdown (strict vs overhead) |

---

## Limitations

1. **Single-Node Local Catalog**: Inspects an in-memory inverted index of 1,600 catalog products; not an Elasticsearch/OpenSearch distributed cluster.
2. **No Synonym / Semantic Expansion**: Explanations reflect keyword stemming and token document frequency; does not explain semantic embedding distances or vector projections.
3. **Static Catalog Evidence**: Document frequencies reflect current catalog inventory state rather than historical inventory snapshots.
